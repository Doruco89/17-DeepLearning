# 3_notes.md — `3.ipynb` 수치 기록 (v5, 최종)

`3.ipynb`(데이터 정제 반영 재구축)와 짝을 이루는 수치 기록 파일. `1.ipynb`(정제 전)와 비교하는 것이 이 노트북의 핵심 목적이라, 표마다 1.ipynb 수치를 나란히 적는다.

**버전 이력**: 1차(전처리/lr을 `1.ipynb`에서 이월) → 2차(전체 그리드 재탐색, 그러나 lr 미니스윕 방식에 결함 발견) → 3차(v3 — lr 후보 전부 최종 설정으로 완전학습해서 비교, 128px 기준으로는 방법론적으로 가장 정확) → 4차(v4, 11절 — 입력 해상도 128→224로 교체) → **5차(v5, 11-1절 — 224px 안에서 lr을 5e-05→1e-04로 교체, 이 문서의 최종 기준)**. 아래 4~9절 수치는 v3 시절 기록이고(파이프라인 설계 근거로서 여전히 유효), **실제 최종 채택 모델과 test/Grad-CAM/오분류 해석은 11절→11-1절→12절 순으로 갱신된 결과를 따른다.** 1·2차 실행 기록은 아래 "버전별 시행착오"에 남긴다.

## 실행 환경

- torch 2.13.0+cu130 / torchvision 0.28.0+cu130, GPU: NVIDIA GeForce RTX 5060 Laptop GPU
- `torch.manual_seed(42)`, `torch.backends.cudnn.deterministic=True`, `benchmark=False` (셀 0)

- 정제 전 15,515장 → 제외 31장(완전동일중복 22 + 애매·비사진 9) → **정제 후 15,484장**, 라벨 정정 46장 반영

## unfreeze 학습률 비교 — 시행착오와 방법론 수정

### 실패한 접근 (2차 버전): 4epoch 미니스윕 → 승자만 최종학습

`1.ipynb`처럼 스케줄러 없이 짧게(4epoch) 스윕해서 lr을 고르고 그 값 하나로만 최종(scheduler+조기종료, 15epoch) 학습을 했다.

| lr             |        val_macro_f1 (4epoch 스윕) |
| -------------- | --------------------------------: |
| 5e-5           |                            0.9538 |
| **1e-4** | **0.9629** ← 스윕에서 승자 |
| 3e-4           |                            0.9479 |

이 결과로 `1e-4`를 채택해 최종 학습을 돌렸더니, **조기 종료(patience=3)가 스케줄러가 개입하기도 전인 6epoch째 발동**해 val_macro_f1이 0.9652에 그쳤다 — `1.ipynb`가 `5e-5`로 15epoch을 다 채워 스케줄러 혜택까지 받아 얻은 0.9680보다 오히려 낮았다.

**결론**: 스케줄러·조기종료가 있는 학습 설정에서는, 그 설정을 빼고 진행한 짧은 스윕의 순위가 실제 최종 학습 결과의 순위를 보장하지 못한다. `1e-4`는 빠르게 수렴하지만 그만큼 빨리 정체돼 조기종료로 이어졌고, `5e-5`는 느리게 수렴하는 대신 스케줄러가 lr을 낮춰가며 오래 개선할 여지를 준다.

### 수정한 접근 (v3, 채택): lr 후보 3개를 전부 최종 설정으로 완전 학습

미니스윕을 없애고, `{5e-5, 1e-4, 3e-4}` 전부 scheduler+조기종료(patience=3, 최대 15epoch)로 끝까지 학습한 뒤 val_macro_f1으로 직접 비교했다.

| lr             | 학습 epoch(조기종료 시점) | val_loss | val_accuracy | **val_macro_f1** | val_macro_recall |
| -------------- | ------------------------: | -------: | -----------: | ---------------------: | ---------------: |
| **5e-5** |     15/15 (조기종료 없음) |   0.0869 |       0.9806 |       **0.9731** |           0.9718 |
| 1e-4           |                      9/15 |   0.0940 |       0.9737 |                 0.9600 |           0.9604 |
| 3e-4           |                     13/15 |   0.0895 |       0.9767 |                 0.9658 |           0.9651 |

**`5e-5`가 명확한 승자** — `1.ipynb`의 원래 선택이 정제된 데이터에서도 여전히 최선이었음을 제대로 된 방법으로 재확인. (참고로 이번엔 12epoch째 lr 0.5e-5, 15epoch째 0.5e-6까지 스케줄러가 두 번 더 낮춰서 15epoch 끝까지 계속 개선됨.)

## 최종 test 평가 — test는 이 1곳에서만 사용

| 지표              | 1.ipynb (정제 전, 8차) | 3.ipynb v3 (정제+그리드 재탐색) |    변화 |
| ----------------- | ---------------------: | ------------------------------: | ------: |
| test accuracy     |                 0.9743 |                **0.9773** | +0.0030 |
| test macro F1     |                 0.9682 |                          0.9671 | -0.0011 |
| test macro Recall |                 0.9688 |                          0.9668 | -0.0020 |

**정직한 해석**: 정제 전과 비교해 정확도는 근소하게 올랐지만 macro F1/Recall은 오히려 근소하게 낮다 — 이 차이는 두 실행 사이의 run-to-run 변동(같은 lr=5e-5라도 그 전에 소비된 랜덤 연산 횟수가 달라 가중치 초기화·배치 순서가 서로 다름) 범위 안에 있을 가능성이 높고, "정제가 test 정확도를 크게 끌어올렸다"고 단정할 근거는 아니다. (1차 이월 버전에서는 +0.0044로 더 크게 보였는데, 이 역시 같은 이유로 우연히 유리하게 나온 값일 수 있다.)

**정제 효과가 뚜렷하게 보이는 것은 정확도 숫자가 아니라 오분류 패턴이다** (아래 참고).

클래스별 F1(v3): `clothes` 1.00, `biological` 0.99 — 상위. `plastic` 0.91, `metal` 0.93 — 여전히 하위(재질 혼동, 정제로 해결되는 문제가 아님).

### 오분류 패턴 변화 (v3 최종)

- **정제 전(`1.ipynb`)**: `clothes→shoes`가 실험 내내 상위권 단골 오분류(라벨 오류가 원인, `label_error_detection_method.md` 참고).
- **정제 후 v3 test 상위 오분류 쌍**: `cardboard→paper`(5) = `plastic→metal`(5) > `plastic→paper`(4) = `white-glass→plastic`(4) > 나머지 재질계 혼동 2건씩. `clothes→shoes`는 top-10에 **2건만 남음**(정제 전 대비 극적으로 감소).
- 3번의 실행(v1/v2/v3) 모두에서 공통적으로 `clothes↔shoes` 오분류가 정제 전 수준(20건대)으로 돌아간 적은 없었다 — **라벨 정정 효과 자체는 실행마다 일관되게 재현됨.** 반면 재질계(유리/플라스틱/금속/종이) 혼동 쌍의 순위는 실행마다 조금씩 바뀌는데, 이는 진짜 어려운 사례들 사이의 근소한 우열이라 run-to-run 노이즈에 더 민감한 것으로 보인다.

## 증강 효과 검증 — 증강 있음 vs 없음 (최종 모델 기준)

최종 모델(`unfreeze_lr_5e-05_v3.pt`)과 **완전히 동일한 조건**(비율유지크롭+`WeightedRandomSampler`+unfreeze+lr 5e-5+스케줄러+patience 3, 최대 15epoch)에서 train transform만 증강 없이(eval transform과 동일)로 바꿔 `unfreeze_lr_5e-05_noaug_v3.pt`를 별도로 학습.

|                   | val_macro_f1 | test accuracy | test macro_f1 |
| ----------------- | -----------: | ------------: | ------------: |
| 증강 O(최종 모델) |       0.9731 |        0.9773 |        0.9671 |
| 증강 X(비교용)    |       0.9595 |        0.9734 |        0.9616 |
| 차이(O-X)         |      +0.0136 |       +0.0039 |       +0.0055 |

**검정 결과(팀 노트북 `3P_09_Team_Analysis_MD.ipynb` "검정 5"에서 수행)**: 같은 test 2,334장에 대한 두 모델의 짝지은 예측을 부트스트랩(2,000회) macro-F1 차이 95% CI와 McNemar로 비교 — CI [-0.0059, 0.0159]가 0을 포함하고 McNemar p=0.3355로, **test 기준으로는 증강 효과가 통계적으로 유의하지 않음**. val에서는 뚜렷한 차이(0.0136)가 났지만 test(0.0055)에서는 줄어들었다.

**해석**: val 차이가 test에서 절반 이하로 줄어든 것은 val 선택 과정 자체가 어느 정도 val에 최적화됐을 가능성(선택 편향)과, 표본 크기(test 2,334장)에서 이 정도 효과크기를 유의하게 잡기엔 검정력이 부족할 가능성 둘 다로 해석 가능. 최종 모델의 증강 채택 자체를 뒤집을 근거는 아니지만(방향은 일관되게 양수), "증강이 확실히 이득"이라고 단정할 근거도 아니다 — 팀 한계 섹션의 "증강 효과가 조건에 따라 뒤집힌다"는 서술을 뒷받침하는 실측 근거가 됨(이전에는 이 수치를 낸 코드가 저장소에 없었음).

**주의(13절 이후)**: 팀 노트북의 "검정 5" 코드는 원래 "증강 O"를 전역 변수 `test_probs`(= 그때그때의 최종모델)로 가져왔다. 이후 최종모델이 v5(224px, lr=1e-04)로 바뀌면서 이 방식으로는 해상도·lr까지 함께 바뀐 것과 증강 여부가 뒤섞여버려, `results/pre_v5_backup/probs_test.npy`(v5로 덮어쓰기 전 백업 — 위 표의 128px/lr=5e-5/증강 O와 동일)를 직접 불러오도록 코드를 고쳤다. 이 절의 수치(0.9671/0.9616, CI, McNemar p=0.3355)는 그대로 유효하다 — v5와는 무관하게 128px 시절에 고정된 비교다.

| 128px 3lr(5e-5/1e-4/3e-4) 앙상블(재학습 없음) |           0.9748 |
| **224px 단일모델(신규 채택)**           | **0.9787** |

224px가 val 기준으로 앙상블보다도 앞서 최종모델로 채택. test 평가(1회): accuracy 0.9773→**0.9854**(+0.0081), macro F1 0.9671→**0.9786**(+0.0115) — plastic(F1 0.9105→0.9575)/metal(0.9333→0.9617) 등 재질 클래스 개선이 큼(상세: `results/resolution/`).

**주의**: 6~9절(최종 test 평가/Grad-CAM/오분류 확인)은 아직 v3(128px) 모델 기준으로 실행된 상태이며, 이번 11절 갱신으로 다시 실행하지 않았다(이후 11-1절에서 최종모델이 다시 v5로 바뀌었으므로 아래 11-1절 참고).

128px 3lr 앙상블은 val 기준으로 224px에 못 미쳐 채택하지 않았지만, test 성능(accuracy 0.9850/macro F1 0.9790)은 224px 재학습 없이 얻은 값이라 배포 시 재학습이 부담스러우면 대안으로 고려 가능(`results/cheap_experiments/`).

## 11-1절 — 224px 내부 lr 앙상블 검토 (사용자 질문: "224px도 앙상블로 해봐야 하는거 아니냐")

128px에서는 3lr 앙상블이 노이즈보다 뚜렷이 컸으므로(+0.0119), 224px에서도 같은지 실제로 검증. lr 1e-4/3e-4를 224px로 새로 완전학습(`results/resolution/lr_sweep_224.py`)해 val로 비교:

| 224px 후보                         |     val_macro_f1 |
| ---------------------------------- | ---------------: |
| 단일 lr=5e-05(v4, 기존)            |           0.9787 |
| **단일 lr=1e-04(신규 채택)** | **0.9840** |
| 단일 lr=3e-04                      |           0.9738 |
| 3lr 앙상블(재학습 없음)            |           0.9846 |

- 224px 안에서는 **1e-04가 5e-05보다 val 기준으로 더 좋음**(+0.0053) → 128px에서 최적이었던 lr(5e-05)이 224px에서도 최적이라는 보장은 없다는 걸 확인. lr=1e-04 단일모델을 v5로 채택, test 1회 공개: accuracy 0.9854→**0.9859**, macro F1 0.9786→**0.9787**(거의 변화 없음 — val에서 본 +0.0053 격차가 test에는 거의 반영되지 않아, 이 격차 자체도 상당 부분 노이즈였을 가능성이 있음. 다만 CLAUDE.md 규칙상 채택 판단은 val로 이미 내렸으므로 test 결과를 이유로 되돌리지 않음).
- **3lr 앙상블(0.9846)은 224px 최고 단일모델(0.9840)과 차이가 +0.0006뿐**으로 시드 노이즈 기준선(0.0046)보다 훨씬 작음 → 224px에서는 앙상블이 확실한 추가 개선을 주지 못함(단일모델 성능이 이미 0.98대라 짜낼 여지가 적었던 것으로 해석). 상세: `results/noise_findings/NOISE_FINDINGS.md` 4번 항목, 시각화 `results/noise_findings/4_224px_3lr_앙상블은_단일모델보다_유의하지_않음.png`.

**주의**: 6~9절(최종 test 평가/Grad-CAM/오분류 확인)은 여전히 v3(128px, lr=5e-05) 모델 기준으로 실행된 상태이며, 11절/11-1절 갱신으로도 다시 실행하지 않았다 — 완전히 일관성을 맞추려면 6~9절을 v5(224px, lr=1e-04) 모델로 재실행해야 함(→ 아래 12절에서 수행).

## 12절 — 최종 모델(v5) 기준 재평가: test / Confusion Matrix / Grad-CAM / 오분류 전수 확인

7~9절을 v5(224px, lr=1e-04) 모델 기준으로 다시 수행해 해석(Grad-CAM 등)이 실제 최종모델과 어긋나 있던 문제를 해소했다. 6절의 5-후보 비교표(v3, 128px 아키텍처/lr 선택 기록)는 그대로 두고 다시 계산하지 않았다 — 11절/11-1절이 해상도·lr을 별도로(val 기준) 재선택했으므로, 12절이 실제 채택된 v5의 최종 해석을 담당한다.

- **test 결과**: accuracy=0.9859, macro F1=**0.9787**, macro Recall=0.9790 (11-1절 test 1회 공개 수치와 정확히 일치 — 재현성 확인됨).
- **오분류 33건**(v3/128px 시절 53건 대비 대폭 감소) — 상위 오분류 쌍은 `white-glass↔plastic`(5+4건), `cardboard→metal`(2건), `white-glass→metal`(2건) 등 여전히 재질/색상 혼동 위주.
- 확신도 최상위 오분류 중 `paper8.jpg`(실제 paper, 예측 plastic, 확신도 0.995)가 다시 등장 — 이전 세션에서 육안으로 "빨간 줄무늬 비닐 포장지, plastic이 맞아 보임"이라 판단했던 것과 **모델의 예측이 일치**함(라벨오류 후보라는 기존 판단을 재확인). `trash640.jpg`(칫솔, trash→shoes 오분류)도 재등장 — `2.ipynb`의 "흰배경+세로물체" 패턴과 일치.
- Grad-CAM: 잘 맞춘 예시 3장 + 상위 오분류 쌍 5장에 대해 224px 기준으로 재시각화(노트북 51~55번 셀 이미지 출력 참고).
- 실행 방법: `jupyter nbconvert --execute`로 별도 노트북을 실제 커널(`.venv`, python3)에서 실행해 텍스트+이미지 출력을 그대로 얻은 뒤 `3.ipynb`에 병합(47→56셀). 커널 상태에 의존하지 않고 재현 가능.

## 13절 — 최종 산출물 갱신: v5 기준 probs/preds + 팀 노트북 재실행

`3.ipynb`에 "## 13. 최종 산출물 갱신" 절을 추가해 `dump()`를 v5(224px, lr=1e-04) 모델 기준으로 다시 실행했다. 프로젝트 루트의 `probs_val.npy`/`probs_test.npy`/`preds_val.csv`/`preds_test.csv`가 이제 v5 기준으로 갱신됐다(갱신 전 값은 `results/pre_v5_backup/`에 백업). `split_hj.csv`는 분할 구성 자체가 안 바뀌므로 다시 쓰지 않았다.

이 파일들을 입력으로 읽는 `3P_09_Team_Analysis_MD.ipynb`(팀 최종본)도 `jupyter nbconvert --execute`로 처음부터 끝까지 재실행해 반영했다(39셀, 오류 0건). 팀 노트북 재실행 과정에서 발견·수정한 것:

- **`result["final_model"]` 문자열**이 `"lr 5e-5"`로 하드코딩돼 있던 걸 `"img=224, lr=1e-4"`로 갱신.
- **검정 5(증강 효과) 코드의 잠재적 혼입 버그를 미리 수정**: 이 검정은 "증강 O"를 전역 `test_probs`(그때그때의 최종모델)로 읽어왔는데, 최종모델이 v5로 바뀐 뒤 그대로 뒀다면 해상도·lr 변화와 증강 여부가 뒤섞여 검정이 무효가 될 뻔했다. `results/pre_v5_backup/probs_test.npy`(128px/lr=5e-5/증강 O)를 직접 불러오도록 고쳐 원래 의도(증강 변수만 격리)를 유지했다 — 위 "증강 효과 검증" 절의 "주의(13절 이후)" 참고.
- 재실행 후 `team_analysis_summary.json`의 `test` 블록(accuracy=0.9859, macro_f1=0.9787)은 v5 기준으로, `augmentation_ablation` 블록(0.9671/0.9616)은 여전히 128px 기준으로 — 두 블록이 서로 다른 모델을 가리킨다는 걸 `note` 필드에 명시했다.
- `fig_*.png` 8장 전부 재생성됨(수치는 대부분 무관하지만 파일 자체는 최신 실행 결과로 갱신).
